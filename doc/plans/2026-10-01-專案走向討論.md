## 起因

- 檢索功能(GPSS 批次檢索、檢索進度、達標分析)已經很少用,但**流量監控還是需要**。
- 新功能(690 資轉監控,見 [2026-10-01-690資轉監控實作計畫.md](2026-10-01-690資轉監控實作計畫.md))
  和**流量報表**要加,而且版面可能會跟著改。
- 原本在考慮:新功能改加到 `TIPO flow check`(流量監控獨立版),`flow_check` 維持現狀。

## 兩個專案的現況(2026-10-01 比對)

| | flow_check `v7.6.0` | TIPO flow check `v3.3.0` |
|---|---|---|
| 程式結構 | 已拆成模組(`estats` / `sampler` / `quota` / `routes` / `storage`…),有共用的 `common/webapp` | 整支 `traffic_monitor.py`(1565 行),是架構優化前就分出去的舊版 |

## 已決定

1. **新功能不加在 TIPO 版那份舊程式上。** 那份程式是架構優化前的結構,加功能等於先把優化重做一次,
   之後每個功能也都得寫兩份。
2. **先補齊兩版的差異**(已完成,見下節)。
3. **同事版一定要有流量報表。**(使用者 2026-10-01 提出)

## 已完成:補齊差異

比對方式:逐個函式比對 TIPO 版 `traffic_monitor.py` 與 flow_check 各模組,另外比對 API 路徑、
config 鍵、前端函式和元素 id。

**結論:流量計算的核心兩邊一樣。** IPv6、今日程式排行、`local_ranges`、svchost 服務名稱、
逐分鐘明細,flow_check 原本就都有。其他差別多半只是重構後寫法不同
(例如改用 `write_json_atomic`、`read_json`),邏輯一致。

真正缺的兩項已經補上(分支 `sync-tipo-diff`):

| 項目 | 處理 |
|---|---|
| 內網排除診斷 `program/core/lan_diag.py` + `diag_lan.bat` | 從 TIPO 版複製過來;匯入改成 `core.estats` / `core.storage`(原本是從 `traffic_monitor` 匯入)。一般權限下實際跑過,能啟動並做到管理員權限檢查;**以管理員身分的完整報表還沒跑** |
| 網卡分頁的捲動外框 | `web/partials/monitor.html` 補上 `.nic-scroll` 包裹層(CSS 兩邊原本就有) |

兩邊不一樣、但**不需要補**的地方:

- 逐分鐘明細的資料夾名稱不同:TIPO 版是 `%LOCALAPPDATA%\tipo_flow_check\traffic`,
  flow_check 是 `%LOCALAPPDATA%\flow_check\traffic`。合併時要處理(見下方「待做」第 2 點)。

## 目前的建議方向(待使用者確認)

**只維護一份程式:flow_check 當主版本,同事版(TIPO flow check)用腳本從它產生,不再手動改。**

- 報表只寫一次,同事版自動帶到。各寫一份的話,同事那份遲早又落後;這次比出來的差異就是這樣來的。
- 產生同事版時只放流量監控和報表,不放 `program/gpss/`、檢索相關頁籤和 API 金鑰,
  同事那邊照樣只需要 Python 加 psutil。
- 檢索功能先不刪。之後在 `config.json` 加 `enabled_tabs` 之類的開關,自己的版本也可以關掉。

### 要做的重構

1. **把檢索拆成可以不放的部分。** 現在 `routes.py` 會匯入 `quota`,`storage.py` 會匯入 gpss,
   拿掉 `program/gpss/` 就啟動不了。要改成像前端頁籤那樣,各功能自己登記路由,少了哪一包就不登記。
2. **同事的舊資料要搬。** 存檔路徑不同:TIPO 版是 `data/state_*.json`、`data/prefs_*.json`、
   `data/machines.json`;flow_check 是 `data/machines/` 和 `data/config/machines.json`。
   逐分鐘明細的資料夾也不同(見上)。同事升級時要自動搬過來,不然用量和明細會歸零。
3. **報表的資料來源要先決定。** 逐分鐘明細只保留 31 天。報表要看月或更長的區間,
   就得另外存一份每日彙總,而且越早開始存,報表能看的資料就越多。

### 建議的順序

```
⬜ ① 把檢索拆開 + 產生同事版的腳本 + 搬舊資料
⬜ ② 流量報表(兩版同時有)
⬜ ③ 690 資轉監控(只在自己的版本)
```

## 已完成:每日用量統計(2026-10-02,未 commit)

越早開始存,報表能看的天數越多,所以先把「存」做起來,報表頁面之後再做。

- `program/core/daily_stats.py`:每天一筆,存 `data/machines/daily_stats_<機器>.json`(長期保留,一天只寫一次)。
  欄位:總量、ssh / vscode / claude 各自的 [收, 發]、未歸因、監控未執行期間、已排除內網。
- 依**程序檔名**歸類:`ssh.exe`、`Code.exe`、`claude.exe`;`config.json` 可用 `report_apps` 改。
- 換日時由當天累計結算;監控跨日沒開,下次啟動時補結算存檔裡那天。
- **只收實際記錄**(2026-10-02 使用者決定):不再用逐分鐘明細回推估算。
  先前已回推寫進檔案的估算日(`source: "log"`)讀取時濾掉,下次換日寫檔就從檔案消失。
- API:`GET /api/traffic/daily`(今天那筆即時算)。
- 用假網卡計數器測過:回推、當日即時、換日結算、跨日重啟補結算都正確。

**報表頁面(2026-10-02):** 使用者自己截圖給公司,只要每天的明細,**用圖表呈現**(不要表格)。
- 新頁籤「流量報表」(`web/partials/report.html` + `web/js/report.js`),排在流量監控後面。
- 每天一根堆疊柱:由下往上 ssh(藍)、Claude Code(橘)、VS Code(青綠)、其他(灰,= 總量扣掉三項);
  柱頂標當天總量。**只畫有紀錄的日子**(沒紀錄的不佔位置)。不另列「對不到程式」,併在「其他」裡。
- **點某一天 → 同一個圖表區塊直接換成那天的逐時圖**(X 軸 **8–20 點**,每個鐘點都標),
  標題前「← 每日」回到每日圖。逐時是**折線圖**(ssh / Claude Code / VS Code 各一條、同一刻度),
  才看得出彼此有沒有同時段一起升降;滑到某個鐘點出現十字線與該小時三項 + 總量。
- **顏色取自系統主題**:ssh = 主色紫 `--btn`、Claude Code = 強調橘 `--accent`、VS Code = 藍 `--blue`
  (原版外觀用較深的 `--blue-ink`,淺藍跟原版紫分不開)、其他 = 進度條底色 `--track`;
  切換深色 / 淺色 / 原版時跟著換。三種外觀的配色都跑過色盲分離度檢查。
- 切換:合計 / 上傳 / 下載(兩種畫面都套用);期間是下拉選單:最近 14 / 31 天(有紀錄的天數)/ 全部
  (逐時畫面用不到,會先藏起來)。
  滑鼠移到柱子顯示各項量與占比;每日數字表收在「看每日數字」。期間總量的統計卡已移除。
- 逐時資料:每日統計多存 `hours`(每小時的總量與三支程式),取樣時即時累計,跨重啟存在 state 的
  `day_hours`。逐時功能上線前的時段沒有逐時資料(不回推)。
- 配色用 dataviz 驗證工具在深/淺底各跑過(色盲分離度、對比)。深色、淺色、原版三種外觀與手機寬度都截圖確認過。
- 用獨立的測試伺服器(port 8799、資料導到暫存夾)測試,沒有 JS 錯誤。

注意:
- 程式別的量要**管理員身分**才抓得到(ESTATS);沒提權時全部落在「未歸因」,只有總量可信。
- Claude Code 若是在公司那台跑(透過 ssh 連過去),它的流量在本機看到的是 **ssh.exe**,不是 claude.exe。
