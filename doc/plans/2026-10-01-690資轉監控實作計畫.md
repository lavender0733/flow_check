# 690 資轉監控 — 實作計畫

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 主工具多一個「690資轉」頁籤。伺服器定時從 Gmail 讀 s690 Rundeck 的通知信,判定每個轉置系統在每一期或每一天、每個步驟是成功、失敗、無資料還是沒跑,顯示在儀表板上;完成的格子,自動在 Wiki.js「資料轉置登記」子頁現有的表格裡登記(打 `v` 或填筆數)。

**Architecture:** 新增獨立套件 `program/xfer690/`。純邏輯三層:解析信件、判定狀態、編輯 markdown 表格的儲存格。對外連線兩支:Gmail REST、Wiki.js GraphQL。`service.py` 負責組裝,結果快取在各機一個 JSON。抓信**以 metadata 為主**(只取主旨和時間),只有少數信件才下載全文。主伺服器只多一條背景執行緒和兩個端點。前端照 7.3.1 的頁籤註冊做法,丟兩個新檔。寫 wiki 時**只填空白儲存格**,目標格以外的字元一律不動。

**Tech Stack:** Python 3.13 標準函式庫(`email`、`html.parser`、`urllib`、`threading`);相依套件 `google-auth-oauthlib`(2026-10-01 已裝在這台的 py -3.13);Gmail REST v1(唯讀);Wiki.js 2.x GraphQL;前端為傳統 `<script>`。

**Spec:** 沒有另寫設計文件。下方「需求」、「信件實況」、「Wiki 現況」、「系統對照」四節,是 2026-10-01 整理自使用者的回答、範例信、**實際用唯讀授權讀取信箱的結果**,以及 wiki 頁面。這份計畫本身就是規格。

## 信件實況(2026-10-01 用唯讀授權讀信箱)

**數量與時間**
- 篩選條件 `list:tipo.innovue.ltd subject:"[s690]"` 在近 30 天抓到 **227 封**,跟只用主旨篩選的結果一樣,沒有漏信。全部集中在 **2026-09-29 之後**,可見逐步通知是那時才開啟的。

**每一個步驟都會寄一封信**(這一點推翻了前一版計畫的假設)
- 母 job(`012000-techreport-pdf-auto | 01-tw/00-auto-schedule`)寄一封,**底下每個子步驟也各寄一封**:`012001-techreport-pdf-step1-raw | 01-tw/20-techreport-pdf`、`012002-…-step1-raw-check`……。
- 所以**只看主旨**就知道每個步驟成功或失敗。不需要從 log 推算失敗在哪一步。
- 主旨格式:`🔴【FAILURE】[s690] <6 碼代碼>-<名稱> | <群組路徑>`。emoji 🔴 / 🟢 是信件本身就有的。主旨是 RFC 2047 編碼、會折成兩行,用 `email.policy.default` 或 Gmail API 的 metadata 都會拿到解碼好的完整字串。
- 時間:metadata 的 `Date` 標頭有時區(`+0800`),也跟內文的 Started / Finished 吻合,直接用它就好。

**.log 附件**(只在下載全文時才拿得到)
- 開頭幾行是 `RUNDECK:DATA:<KEY>=<VAL>`,也就是**這次跑的是哪一期**。實際看到的 key:
  - 書目、雜項、全文:`VOL=2419`、`TAG=20261001`
  - posted 系列:`DOWNLOAD_DATE=20260930`、`TAG=…`
  - 技術報告:`VOL_DATE=1151001`(民國日期)
  - 英譯:`FILE_I=TW__I_…`、`FILE_M=…`、`TAG=…`
- **log 是累積的**:後面步驟的 log 包含前面步驟的內容,所以 posted-legal L1 的 log 有 31,370 行。
- 筆數:`[job_complete] <名稱> … writes=<N> … fail=<M>`,以及 `Total data count: <N>`。
- 失敗時有 `error: <原因>`,例如 `GCS 資料夾無檔案: gs://…/1151001`(當天沒資料)。
- log 裡有遮蔽過的連線資訊。程式只取上面這幾種資訊,**不保存整份 log**。

**Q2:筆數欄的值從 log 來,再跟人填的值比對**(2026-10-05 改成這個順序)
- **做法:先從 log 抓值,再去比對 wiki 上人填的值是否相同。** log 是來源,wiki 上人填的值是被檢查的對象,不是拿 wiki 的值去 log 裡找吻合的數字。

## Global Constraints

- 版號 `7.6.0` → **`7.7.0`**(唯一來源 `program/core/traffic_monitor.py` 的 `VERSION`)。
- 頁籤 id `xfer690`、按鈕文字 `690資轉`、`order: 50`。檔名符合 `^[a-z][a-z0-9_]*$`。
- Gmail scope 只用 `https://www.googleapis.com/auth/gmail.readonly`。

- 對每個系統先 `group_runs`,每一段裡第一個有 VOL / 日期的事件決定 `run_period`,再對每個事件求 `period_of`。期別是 None 的事件只顯示在「最近事件」,不進表格。
- 同一期、同一步驟有多封信時,取 `at` 最晚那封;`runs` 是封數。
- 某期中只要有一封 `nodata`,整期的每個步驟都視為 `nodata`。期別系統的 `nodata` 在算整體 state 和 alerts 時當成 `fail`;`cell_done` 也只對每日系統的 `nodata` 回 True。
- **步驟層的 missing / pending**:一期只要收到任何一封信,系統 `steps` 裡沒收到信的步驟,就依「該期日期的 `expect_by`」判定:還沒到 → `pending`,過了 → `missing`。期別系統沒有固定的時刻,改用「該段最後一封信之後 2 小時」當期限。
- 整體 state 依序取第一個成立的:有 `fail` → fail;有 `missing` → missing;有 `unknown` → unknown;有 `pending` → pending;全部是 nodata → nodata;其他 → ok。
- **預期的期別**(時窗是 `[今天 − days + 1, 今天]`):`daily` → 每一天;`monthdays` 加上 `vol_twb` / `vol_twa` → 每個排程日換算成期別;`manual` 或 `period == "vol"` → 沒有預期。預期中卻沒有任何事件的期別:是今天的而且 `now < expect_by` → `pending`,否則 → `missing`。
- `tag` = 該期任一事件 `data["TAG"]`。
- `alerts` = `configured` 系統在時窗內 state 屬於 `fail` / `unknown` / `missing` 的期數。

另外提供 `cell_done(period: dict, step: str, check: str | None) -> bool`:有 check 就看 check 的 state 是 ok;沒有 check 就看 step 本身是 ok;`nodata` 一律 True。
