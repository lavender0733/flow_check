# 傳統(Web)檢索 — 網路流量問題與優化說明

> 紀錄日期:2026-06-12　對象檔案:`gpss_web_query.py`

## 問題起點

某次跑 500 筆傳統檢索,程式只回報「網路流量總計:28.6 MB」,但當天系統實際網路使用卻高達 **1.153 GB**,帳對不起來。API 版則沒有這個現象。

## 三個真正的原因(依序發現)

1. **舊計法嚴重低估流量**
   舊版流量計只把每個回應的 `Content-Length` 標頭加總。但 TIPO 後端的動態回應多為 `Transfer-Encoding: chunked`、**不帶 `Content-Length`**,於是被當成 0、完全沒算到。自報 28.6 MB、真實近 1 GB 就是這樣來的。

2. **真兇:靜態 JS 被重複下載**
   傳統檢索是用 Playwright 開真的 Chromium,**每查一筆就完整載入一次前端頁面**;TIPO 對 JS 包送 no-cache,連同一個 context 內都不快取,導致那 28 個 JS 包**每筆查詢都整套重抓**。實測佔總流量約 **95%**——這才是吃掉那 1 GB 的元兇,而舊計法剛好看不到它(chunked)。

3. **本機網路有 SSL 攔截**
   某些機器在公司 SSL 檢查/攔截網路下,根憑證只裝在 Windows 系統憑證庫、Node 不認,導致最初用 `route.fetch()` 做快取時每次都丟「unable to verify the first certificate」而失效。

## 採用的解法(都在 `gpss_web_query.py`)

| 問題 | 解法 |
|---|---|
| 流量算不準 | 改用 CDP `Network.loadingFinished.encodedDataLength` 量「實際上線位元組」(含標頭/壓縮/chunked) |
| JS 重複下載 | 加「行程內快取」`_ASSET_CACHE`:同一 script URL 第一次由瀏覽器正常下載、用 `response.body()` 抓進快取;之後所有查詢(跨批、跨 context)用 `route.fulfill` 從記憶體餵回,不再連線 |
| SSL 攔截卡 `route.fetch` | 不走 Node 的 `route.fetch`,改用瀏覽器自己下載 + `response.body()` 擷取,完全繞開憑證問題 |
| `fulfill` 餵回的量被計數器誤算成流量 | 餵回時加 `x-cache-hit` 標頭,CDP 計數時辨識並排除(那些未走網路) |
| body 已解壓卻沿用原標頭 | 快取時移除 `content-encoding`/`content-length`/`transfer-encoding`,避免瀏覽器二次解壓毀檔 |

只快取 `script`(含 session token 的 document/XHR 維持即時,不快取)。

## 成效(實測)

- **20 筆**:9.8 MB → **2.1 MB**(每筆 500 KB → 106 KB),20/20 全成功。
- **500 筆**:約 900 MB(其中 JS ~887 MB)→ **11.5 MB**,Script 僅 1.1 MB,**省約 98%**,與 API 版同量級。
- 結尾會印「靜態快取:命中 N 次,從記憶體供應 X(未走網路)」,X 即省下、未走網路的量。
- `[cache debug]` 那行只在異常時(命中 0 或有 fulfill 失敗)才印,用來日後排查。

## 備註

- 程式碼在 Google Drive 同步資料夾,各機同步後一致;沒有 SSL 攔截的機器快取也照樣生效。
- context 建立時的 `ignore_https_errors=True` 是早期為 `route.fetch` 加的,現已不需,但留著對 SSL 攔截網路無害。
- 一般情況優先用 **API 版**(`gpss_api_query.py`,又輕又快);傳統檢索是 API 被管制時的備援,如今流量也已壓到可接受範圍。
